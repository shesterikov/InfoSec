# Практическая работа 2

## Реализация регистрации и аутентификации пользователей

### Цель работы

Получить практические навыки реализации регистрации и аутентификации пользователей в веб-приложении, безопасного хранения паролей и защиты от многократных неудачных попыток входа.

### Технические требования:

- Наличие интернет-соединения
- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/)
- Наличие [cURL](https://curl.se/download.html) / [Postman](https://www.postman.com/downloads/) / [Insomnia](https://insomnia.rest/download)
- Наличие настроенного окружения для работы с выбранным языком программирования (интерпретатор, компилятор, менеджер зависимостей [при необходимости])

### Технические ограничения:
Допускается использование следующих языков программирования и HTTP-фреймворков:
- TypeScript / [NestJS](https://nestjs.com/)
- Java / [Spring Framework](https://spring.io/) / [Spring Boot](https://spring.io/projects/spring-boot)
- Python / [Django](https://www.djangoproject.com/) / [Flask](https://flask.palletsprojects.com/) / [FastAPI](https://fastapi.tiangolo.com/)
- Go / [Gin](https://gin-gonic.com/) / [Fiber](https://gofiber.io/) / [Echo](https://echo.labstack.com/) / [Beego](https://beego.vip/)
- PHP / [Laravel](https://laravel.com/)

### Постановка задачи
Необходимо с нуля разработать небольшой HTTP API для регистрации и аутентификации пользователей.

API должен предоставлять два эндпоинта:

POST /register
POST /login

Необходимо самостоятельно:

- создать проект на выбранном языке программирования и HTTP-фреймворке;
- настроить подключение к PostgreSQL;
- спроектировать структуру базы данных;
- реализовать регистрацию пользователей;
- реализовать аутентификацию;
- реализовать безопасное хранение паролей;
- реализовать защиту от многократных неудачных попыток входа;
- реализовать обработку основных ошибочных ситуаций;
- обеспечить необходимые ограничения целостности на уровне базы данных.

### Ход работы:

1. Запустите инфраструктуру с использованием команды `docker compose up -d --build`

2. Убедитесь, что контейнер PostgreSQL запущен и к базе данных можно подключиться посредством PgAdmin.

3. Спроектируйте модель базы данных
Необходимо самостоятельно спроектировать структуру базы данных для хранения зарегистрированных пользователей.

Структура должна позволять:

- однозначно идентифицировать пользователя;
- хранить адрес электронной почты;
- хранить хеш пароля;
- хранить соль;
- хранить количество неудачных попыток аутентификации;
- определить момент окончания блокировки пользователя.

Минимальный набор полей модели User: id, email, password_hash, password_salt, failed_login_attempts, locked_until

Допускается добавление других необходимых полей.

Конкретные названия полей, их типы и структуру таблиц вы определяете самостоятельно.

4. Добавьте ограничения на уровне модели данных
Необходимо использовать ограничения (constraints) на уровне СУБД.

Как минимум должны быть обеспечены следующие требования:

- идентификатор пользователя должен быть первичным ключом;
- email пользователя должен быть уникальным;
- обязательные поля не должны содержать NULL;
- значения, для которых это необходимо по логике приложения, должны иметь подходящие ограничения.

Проверки уникальности email только в коде приложения недостаточно.

5. Реализуйте эндпоинт регистрации пользователя
Необходимо реализовать эндпоинт `POST /register`

Данный эндпоинт должен принимать данные нового пользователя.

Пример тела запроса:
```
{
    "email": "test@example.com",
    "password": "super_secret_password"
}
```

При успешной регистрации пользователь должен быть сохранен в базе данных.
Пароль не должен храниться в базе данных в открытом виде.

Для каждого пользователя необходимо:
- сгенерировать случайную соль;
- вычислить хеш пароля с использованием этой соли;
- сохранить хеш пароля в базе данных;
- сохранить соль в базе данных отдельно от хеша.

Для генерации хеша рекомендуется использование PBKDF2 / scrypt / Argon2.

Для разных пользователей необходимо использовать разные соли.
Таким образом, при регистрации двух пользователей с одинаковыми паролями значения их хешей должны отличаться.
Допускается использование стандартных библиотек языка программирования и возможностей выбранного фреймворка.

6. Реализуйте эндпоинт аутентификации пользователя
Необходимо реализовать эндпоинт `POST /login`

Данный эндпоинт должен принимать учетные данные пользователя:
```
{
    "email": "test@example.com",
    "password": "super_secret_password"
}
```

При выполнении входа приложение должно:

- найти пользователя по email;
- получить сохраненную соль и хеш;
- вычислить хеш введенного пароля с использованием сохраненной соли;
- сравнить полученный хеш с сохраненным;
- разрешить или запретить вход в зависимости от результата проверки.

При правильном пароле API должен вернуть успешный HTTP-ответ.
Конкретный формат успешного ответа вы определяете самостоятельно.

В рамках данной практической работы не требуется реализовывать JWT, сессии или другие механизмы поддержания авторизованного состояния пользователя.

7. Реализуйте базовую защиту от перебора паролей
Необходимо реализовать ограничение количества последовательных неудачных попыток входа.
Для каждого пользователя необходимо хранить количество неудачных попыток аутентификации.

Минимальная политика:
После 3 последовательных неудачных попыток вход пользователя блокируется на 5 минут.

Во время блокировки попытки входа пользователя должны отклоняться.
После окончания периода блокировки пользователь снова может выполнять аутентификацию.
При успешном входе счетчик неудачных попыток должен быть сброшен.
Для хранения момента окончания блокировки рекомендуется использовать отдельное поле, например `locked_until`
Если пользователь не заблокирован, данное поле может содержать NULL.

8. Реализуйте обработку ошибок
API должен корректно обрабатывать основные ошибочные ситуации.

Необходимо предусмотреть как минимум:

- регистрацию пользователя с уже существующим email;
- регистрацию с некорректными или отсутствующими данными;
- попытку входа с несуществующим пользователем;
- попытку входа с неправильным паролем;
- попытку входа заблокированного пользователя.

Необходимо использовать подходящие HTTP-коды ответа.
Формат сообщений об ошибках вы определяете самостоятельно.

API не должен возвращать клиенту:
- пароль пользователя;
- хеш пароля;
- соль пользователя.

9. Опционально: реализуйте нормализацию email пользователя
Данная часть является необязательной.

Необходимо учесть возможность использования различных вариантов записи одного и того же адреса электронной почты.

В рамках данной практической работы следующие адреса необходимо считать одинаковыми:
- example@example.com
- example+v@example.com
- example+test@example.com

То есть часть после символа `+` в локальной части адреса не должна учитываться при определении пользователя.
