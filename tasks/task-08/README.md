# Практическая работа 8

## Обнаружение уязвимостей удалённого выполнения кода на примере Spring4Shell

### Цель работы

Получить практические навыки обнаружения признаков уязвимостей удалённого выполнения кода в веб-приложениях с использованием автоматизированного сканирования и ручного тестирования.

### Технические требования

- Наличие интернет-соединения
- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/)
- Наличие [cURL](https://curl.se/download.html) / [Postman](https://www.postman.com/downloads/) / [Insomnia](https://insomnia.rest/download)
- Наличие браузера с возможностью настройки HTTP-прокси.

### Постановка задачи

В ходе работы необходимо исследовать веб-приложение на наличие признаков Spring4Shell (CVE-2022-22965), используя средства автоматизированного анализа и ручного тестирования.

В качестве объекта исследования используется приложение на Spring WebMVC 5.3.17. Приложение, сканеры Nuclei и OWASP ZAP, а также сервер обратных взаимодействий Interactsh запускаются в Docker.

Необходимо выполнить следующие действия:

- исследовать параметры и HTTP-ответы приложения;
- изучить локальный шаблон Nuclei и выполнить сканирование;
- проверить результат вручную и сопоставить его с результатом ZAP;
- выполнить проверку официальным шаблоном Nuclei через локальный Interactsh;
- определить причину обнаруженного поведения и ограничения проверок;
- предложить меры защиты;
- повторить проверку после обновления Spring Framework.

Все действия по исследованию и эксплуатации выполняются исключительно в предоставленной практической инфраструктуре.

### Теоретические сведения

Удалённое выполнение кода (Remote Code Execution, RCE) — класс уязвимостей, при эксплуатации которых атакующий может выполнять код на удалённой системе.

Spring4Shell связана с небезопасным связыванием HTTP-параметров со свойствами Java-объектов в Spring Framework. Обращение через `class.module.classLoader` в уязвимой конфигурации позволяет изменять свойства за пределами ожидаемых данных приложения.

Известная цепочка эксплуатации с записью JSP через журналирование Tomcat требует уязвимой версии Spring, JDK 9 или новее, зависимости `spring-webmvc` либо `spring-webflux`, развёртывания приложения как WAR в Tomcat и обработчика, связывающего входные параметры с Java-объектом. Доступ к свойствам ClassLoader сам по себе не подтверждает возможность выполнения команд.

Nuclei выполняет проверки, описанные в YAML-шаблонах. Локальный учебный шаблон сравнивает ответы на контрольный запрос и запрос с некорректным значением свойства ClassLoader. Сочетание HTTP 200 и HTTP 400 рассматривается как признак опасного связывания параметров. Аналогичный подход используется правилом Spring4Shell в ZAP.

Официальный шаблон Nuclei использует Interactsh для регистрации обратного HTTP-взаимодействия Java. В стенде DNS- и HTTP-запросы принимает локальный сервер в домене `oast.test`. Ни локальная проверка, ни обратное взаимодействие не подтверждают выполнение произвольных команд; результаты необходимо анализировать вручную.

Первые исправления Spring4Shell выпущены в Spring Framework 5.3.18 и 5.2.20. В работе используется обновление до 5.3.18 для сравнения поведения приложения. Для реальных систем следует выбирать поддерживаемую версию с актуальными исправлениями безопасности.

### Ход работы

1. Запустите стенд при помощи команды:

```text
docker compose up -d spring zap interactsh
```

2. Проверьте функционирование исходного приложения

Проверьте ответ из терминала:

```text
curl -i 'http://localhost:4000/?name=Bob&age=25'
```

3. Изучите шаблон Nuclei

Откройте файл `templates/spring4shell-local.yaml`.

Определите:

- какие запросы отправляет сканер;
- какой параметр используется для проверки;
- что означает условие `status_code_1 == 200 && status_code_2 == 400`;
- почему срабатывание шаблона не подтверждает RCE.

Шаблон рассчитан на корневой обработчик предоставленного приложения.

4. Проведите автоматизированную проверку Nuclei

Определите версию сканера и запустите проверку:

```text
docker compose run --rm nuclei -version
docker compose run --rm nuclei
```

Параметры запуска заданы в `docker-compose.yml`. Сканер обращается к `http://spring:8080/`, использует локальный шаблон без Interactsh и сохраняет результат в `reports/spring4shell.jsonl`.

Ожидается находка `spring4shell-local-binding-check`. Сохраните версию сканера, параметры запуска и результат для отчёта. Перед повторной проверкой скопируйте файл результата, если он нужен для сравнения.

> Важно: отсутствие находки не доказывает безопасность приложения. Проверьте доступность цели, ответы на запросы и ошибки сканирования.

5. Проверьте результат вручную

Отправьте контрольный запрос и запрос с некорректным значением свойства ClassLoader:

```text
curl -i 'http://localhost:4000/?name=Bob&age=25&aaa=bbb'
curl -i 'http://localhost:4000/?name=Bob&age=25&class.module.classLoader.DefaultAssertionStatus=nonsense'
```

Для исходного приложения ожидаются HTTP 200 и HTTP 400 соответственно.

Сопоставьте ответы с условием срабатывания шаблона. Объясните, почему ответ HTTP 400 без контрольного запроса недостаточен для вывода о наличии уязвимости.

Сохраните запросы и ответы для отчёта.

6. Проведите проверку с помощью ZAP

Откройте http://127.0.0.1:8081/zap в браузере без прокси и дождитесь рабочего окна ZAP.

В отдельном профиле браузера настройте HTTP-прокси `127.0.0.1:8091` и откройте http://target:8080/?name=Bob&age=25. Адрес `target` доступен через прокси внутри Docker-сети. Для этой проверки используется HTTP; установка сертификата ZAP не требуется.

Добавьте `http://target:8080` в контекст и область сканирования (Scope). Выберите режим Protected.

В меню Analyze → Scan Policy Manager создайте политику `Spring4Shell only`:

- установите Threshold `OFF` для всех правил;
- включите только Spring4Shell с Threshold `Medium` и Strength `Medium`.

Запустите Active Scan для перехваченного запроса с этой политикой. Убедитесь, что Java и Spring не исключены в Technologies.

Изучите проверочные запросы на вкладке History. Сопоставьте параметры, ответы и выводы ZAP с результатами Nuclei. Пассивные предупреждения могут появляться независимо от выбранной политики.

Сохраните версию ZAP, настройки и результаты для отчёта. Файлы из контейнера скачайте средствами Webswing.

7. Выполните проверку через локальный Interactsh

Проверьте состояние сервера и его журналы:

```text
docker compose ps interactsh
docker compose logs interactsh
```

Убедитесь, что запущены HTTP на порту 80 и DNS на порту 53. Выполните проверку  шаблоном:

```text
docker compose run --rm nuclei-oast
```

Используется файл `templates/CVE-2022-22965.yaml` и сервер `http://oast.test`. Результат сохраняется в `reports/spring4shell-oast.jsonl`.

Дождитесь завершения сканирования, включая ожидание обратных взаимодействий. Проверьте наличие находки `CVE-2022-22965` и изучите HTTP-взаимодействие, в том числе заголовок `User-Agent` Java.

Объясните последовательность проверки:

- регистрация Nuclei на Interactsh;
- отправка проверочного запроса приложению;
- разрешение имени и обратный HTTP-запрос со стороны Java;
- получение события сканером.

В стенде используется HTTP без публичного TLS-сертификата. Для HTTPS-проверок шаблона возможны ошибки соединения; для срабатывания достаточно подходящего HTTP-взаимодействия. Одного DNS-события недостаточно.

Домен `oast.test` доступен только внутри стенда, порты Interactsh на компьютере не публикуются. При отсутствии результата проверьте журналы приложения и Interactsh.

8. Проанализируйте результаты и способы защиты

На основании проведённых проверок определите:

- какие признаки опасного связывания параметров обнаружены;
- почему похожие результаты Nuclei и ZAP не являются независимым подтверждением RCE;
- какие сведения даёт обратное HTTP-взаимодействие Java;
- какие условия необходимы для выполнения команд;
- как обновление Spring и ограничение связывания параметров устраняют причину уязвимости.

Обоснуйте вывод о том, достаточно ли полученных данных для подтверждения RCE.

9. Проверьте действие обновления Spring Framework

Соберите и запустите приложение со Spring Framework 5.3.18:

```text
docker compose build spring-fixed
docker compose up -d spring-fixed
```

Дождитесь доступности http://localhost:4001/?name=Bob&age=25 и повторите ручную проверку:

```text
curl -i 'http://localhost:4001/?name=Bob&age=25&aaa=bbb'
curl -i 'http://localhost:4001/?name=Bob&age=25&class.module.classLoader.DefaultAssertionStatus=nonsense'
```

Ожидается HTTP 200 для обоих запросов: обработчик работает, а доступ к опасному свойству блокируется при связывании.

Повторите проверку Nuclei с сохранением результата в отдельный файл:

```text
docker compose run --rm nuclei -u http://spring-fixed:8080/ -t /templates/spring4shell-local.yaml -disable-update-check -no-interactsh -jsonl -o /reports/spring4shell-fixed.jsonl -no-color -stats
```

Находка `spring4shell-local-binding-check` не ожидается. Убедитесь, что сканирование отправило запросы и завершилось без ошибок.

Через прокси ZAP откройте http://spring-fixed:8080/?name=Bob&age=25, добавьте адрес в контекст и Scope. Повторите Active Scan с политикой `Spring4Shell only`. Анализируйте результаты нового сканирования: прежнее предупреждение для `target` может сохраниться в сессии.

Составьте таблицу сравнения двух версий: HTTP-ответы, результаты Nuclei и правила ZAP 40045. Объясните, какие выводы позволяет сделать повторная проверка.

10. Подтвердите выполнение команд на учебном стенде (необязательно)

Используя [описание Vulhub](https://github.com/vulhub/vulhub/blob/master/spring/CVE-2022-22965/README.md), воспроизведите Spring4Shell на исходном приложении.

Сохраните результаты сканирования и пересоздайте приложение:

```text
docker compose up -d --force-recreate spring
```

Дождитесь запуска приложения. Изучите запрос из раздела Vulnerability Reproduce и объясните, как изменение настроек журналирования Tomcat приводит к созданию JSP-файла.

Адаптируйте запрос к стенду: используйте `http://localhost:4000` при обращении с компьютера или `http://target:8080` через прокси ZAP. В заголовке `Host` укажите соответствующий адрес и порт.

Отправьте запрос через редактор запросов ZAP, сохранив параметры и специальные заголовки из описания. Затем обратитесь к созданному JSP-файлу с командой `id`:

```text
http://localhost:4000/tomcatwar.jsp?pwd=j&cmd=id
```

Сохраните запрос и ответ. Объясните, чем вывод команды отличается от свидетельств, полученных при сканировании и обратном HTTP-взаимодействии.

Выполните запрос очистки свойства `pattern` из описания Vulhub. Он прекращает запись в JSP-файл, но не удаляет его. Для восстановления исходного состояния пересоздайте приложение:

```text
docker compose up -d --force-recreate spring
```

Убедитесь, что обычная страница работает, а обращение к `tomcatwar.jsp` возвращает HTTP 404.

11. Подготовьте отчёт и остановите стенд

В отчёте приведите:

- версии инструментов и параметры проверок;
- проверочные запросы и условие срабатывания локального шаблона;
- результаты Nuclei, ZAP и проверки через Interactsh;
- сравнение HTTP-ответов и результатов сканирования до и после обновления Spring;
- объяснение обнаруженного поведения, ограничений проверок и способов защиты;
- вывод о наличии признаков уязвимости и подтверждении RCE.

Если выполнялось необязательное задание, добавьте запросы воспроизведения, вывод `id` и результат проверки после восстановления приложения.

Остановите стенд:

```text
docker compose --profile comparison down
```
