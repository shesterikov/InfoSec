# Практическая работа 8

## Обнаружение уязвимостей удалённого выполнения кода на примере Spring4Shell

### Цель работы

Получить практические навыки обнаружения признаков уязвимостей удалённого выполнения кода в веб-приложениях с использованием автоматизированного сканирования и ручного анализа HTTP-запросов и ответов.

### Технические требования

- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/).
- Наличие браузера с возможностью настройки HTTP-прокси.
- Наличие утилиты `curl` для ручной проверки HTTP-ответов.
- Наличие интернет-соединения для загрузки Docker-образов.

### Постановка задачи

В ходе работы необходимо исследовать веб-приложение на наличие признаков Spring4Shell (CVE-2022-22965), используя средства автоматизированного анализа и ручного тестирования.

В качестве объекта исследования используется приложение на Spring WebMVC 5.3.17. Для автоматизированного анализа используются Nuclei с локальным учебным и официальным шаблонами и OWASP ZAP с веб-интерфейсом Webswing. Приложение, инструменты и собственный сервер Interactsh запускаются в Docker.

Необходимо выполнить следующие действия:

- исследовать параметры и HTTP-ответы приложения;
- изучить локальный шаблон Nuclei и условие его срабатывания;
- выполнить автоматизированную проверку признаков Spring4Shell;
- воспроизвести проверочные запросы вручную;
- сопоставить результаты Nuclei и ZAP;
- выполнить проверку официальным шаблоном через локальный Interactsh;
- объяснить причину обнаруженного поведения и ограничения метода;
- предложить меры устранения уязвимости;
- сравнить результаты с приложением после обновления Spring Framework.

Все действия по исследованию выполняются исключительно в предоставленной практической инфраструктуре.

### Теоретические сведения

Удалённое выполнение кода (Remote Code Execution, RCE) — класс уязвимостей, при эксплуатации которых атакующий может выполнять код на удалённой системе.

Spring4Shell (CVE-2022-22965) связана с небезопасным связыванием HTTP-параметров со свойствами Java-объектов в Spring Framework. В уязвимой конфигурации обращение к свойствам через `class.module.classLoader` позволяет выйти за пределы ожидаемых данных приложения.

Для известной цепочки эксплуатации с записью JSP через журналирование Tomcat необходимы следующие условия:

- уязвимая версия Spring Framework: 5.3.0–5.3.17 либо 5.2.19 и более ранние;
- JDK 9 или новее;
- зависимость `spring-webmvc` либо `spring-webflux`;
- приложение развёрнуто как WAR в Apache Tomcat;
- доступный HTTP-обработчик связывает входные параметры с Java-объектом, позволяя обратиться к опасным свойствам.

Эти условия относятся к известной цепочке эксплуатации. Развёртывание Spring Boot в виде исполняемого JAR не подвержено именно этой цепочке, но само по себе не заменяет обновление уязвимой библиотеки. Доступ к свойствам ClassLoader ещё не доказывает возможность записи JSP или выполнения команд. Подробнее: [описание CVE от Spring](https://spring.io/security/cve-2022-22965/).

Первые исправления этой CVE выпущены в Spring Framework 5.3.18 и 5.2.20. В сравнительном опыте используется 5.3.18, чтобы показать эффект минимального обновления; для реального приложения следует выбирать поддерживаемую версию с актуальными исправлениями безопасности.

Nuclei выполняет проверки, описанные в YAML-шаблонах. Шаблон определяет отправляемые запросы и условия, при которых сканер сообщает о находке.

В работе используется локальный учебный шаблон `templates/spring4shell-local.yaml`, основанный на подходе правила Spring4Shell в ZAP. Он сравнивает ответы на обычный запрос и запрос с некорректным логическим значением свойства ClassLoader. Сочетание HTTP 200 для контрольного запроса и HTTP 400 для проверочного рассматривается как признак опасного связывания параметров.

Локальный шаблон не записывает файлы и не выполняет команды на сервере. Его срабатывание является эвристическим признаком потенциальной уязвимости и не подтверждает возможность выполнения произвольного кода. Возможны ложные результаты, поэтому ответы приложения необходимо проанализировать вручную.

Официальный шаблон Nuclei для CVE-2022-22965 использует Interactsh — сервис регистрации обратных сетевых взаимодействий. В стенде собственный Interactsh принимает DNS- и HTTP-запросы во внутренней сети Docker. Spring использует его для разрешения генерируемых имён в домене `oast.test`, а Nuclei регистрирует проверку и получает события по HTTP. После загрузки образов доступ в интернет не требуется для обоих способов проверки.

Официальный шаблон сохранён в файле `templates/CVE-2022-22965.yaml`. Он проверяет исходящее HTTP-взаимодействие Java, но также не выполняет произвольные команды на сервере.

### Ход работы

1. Запустите стенд

Откройте терминал в каталоге `task-08` и загрузите образы:

```text
docker compose pull spring nuclei zap interactsh
```

Запустите приложение, ZAP и Interactsh:

```text
docker compose up -d spring zap interactsh
```

Откройте http://localhost:4000/?name=Bob&age=25 и дождитесь появления страницы приложения.

При ошибках проверьте состояние контейнеров командой `docker compose ps` и журналы командой `docker compose logs spring zap interactsh`.

Если приложение ранее изменялось при воспроизведении эксплуатации, пересоздайте его перед проверкой командой `docker compose up -d --force-recreate spring`.

2. Проверьте функционирование исходного приложения

Откройте страницу с разными значениями параметров `name` и `age`.

Определите:

- какие параметры передаются в запросе;
- как значения параметров отражаются на странице;
- какой HTTP-статус возвращается при корректном запросе.

Проверьте ответ из терминала:

```text
curl -i 'http://localhost:4000/?name=Bob&age=25'
```

Ожидается HTTP 200. Сохраните запрос и ответ для отчёта.

3. Изучите шаблон Nuclei

Откройте файл `templates/spring4shell-local.yaml`.

Определите:

- какие два запроса отправляет сканер;
- какой параметр используется для проверки;
- как условие `status_code_1 == 200 && status_code_2 == 400` связано с ответами приложения;
- почему шаблон сообщает о потенциальной уязвимости, но не подтверждает RCE.

Шаблон рассчитан на корневой обработчик предоставленного приложения. Для проверки другого приложения необходимо учитывать путь обработчика и формат принимаемых данных.

4. Проведите автоматизированную проверку Nuclei

Определите версию сканера:

```text
docker compose run --rm nuclei -version
```

Запустите проверку:

```text
docker compose run --rm nuclei
```

В сети Docker приложение доступно сканеру по адресу `http://spring:8080/`. Адрес `localhost` внутри контейнера относится к самому контейнеру.

Параметры проверки заданы в `docker-compose.yml`:

- используется локальный шаблон `templates/spring4shell-local.yaml`;
- проверяется корневой обработчик приложения;
- отключены проверки обновлений и использование Interactsh;
- результат сохраняется в формате JSONL в `reports/spring4shell.jsonl` на компьютере.

Ожидается находка с идентификатором `spring4shell-local-binding-check`. Сохраните версию Nuclei, параметры запуска и результат для отчёта. Перед повторным запуском скопируйте файл результата под другим именем, если он нужен для сравнения.

При отсутствии находки проверьте доступность приложения, ответы на оба запроса и журналы контейнера `spring`. Отсутствие находки само по себе не доказывает безопасность приложения.

5. Проверьте результат вручную

Повторите контрольный запрос:

```text
curl -i 'http://localhost:4000/?name=Bob&age=25&aaa=bbb'
```

Повторите запрос с некорректным значением свойства ClassLoader:

```text
curl -i 'http://localhost:4000/?name=Bob&age=25&class.module.classLoader.DefaultAssertionStatus=nonsense'
```

Для исходного стенда ожидаются HTTP 200 и HTTP 400 соответственно.

Сопоставьте ответы с условием срабатывания шаблона. Объясните, почему один ответ HTTP 400 без контрольного запроса недостаточен для вывода о наличии уязвимости.

Сохраните запросы и ответы для отчёта.

6. Сопоставьте результат с ZAP

Откройте http://127.0.0.1:8081/zap в браузере без прокси и дождитесь рабочего окна ZAP.

В отдельном профиле браузера настройте HTTP-прокси `127.0.0.1:8091` и откройте http://target:8080/?name=Bob&age=25.

Адрес `target` доступен внутри Docker-сети; обращайтесь к нему через настроенный прокси. Используется HTTP, поэтому настройка SOCKS и установка сертификата ZAP не требуются.

Добавьте `http://target:8080` в контекст ZAP и включите его в область сканирования (Scope). Выберите режим Protected.

Откройте Analyze → Scan Policy Manager и создайте отдельную политику `Spring4Shell only`. В редакторе политики установите для всех правил порог срабатывания (Threshold) `OFF`, затем включите только Spring4Shell, Threshold `Medium`, Strength `Medium`. Сохраните политику.

Запустите Active Scan для перехваченного запроса к приложению и выберите политику `Spring4Shell only`. Убедитесь, что Java и Spring не исключены в Technologies. Сохраните настройки политики для отчёта. Пассивные предупреждения могут появляться независимо от выбранных активных правил.

Найдите проверочные запросы на вкладке History. Сопоставьте использованные параметры, HTTP-ответы и выводы ZAP с результатами Nuclei.

Сохраните версию ZAP, настройки, результаты и примеры запросов для отчёта. Отчёты из контейнера ZAP скачайте средствами Webswing.

7. Выполните проверку через локальный Interactsh

Проверьте состояние сервера и его журналы:

```text
docker compose ps interactsh
docker compose logs interactsh
```

В журналах должны присутствовать сообщения о запуске HTTP на порту 80 и DNS на порту 53.

Запустите Nuclei с официальным шаблоном и локальным сервером обратных взаимодействий:

```text
docker compose run --rm nuclei-oast
```

Сервис `nuclei-oast` использует тот же образ сканера, но другие параметры проверки:

- официальный шаблон загружается из файла `templates/CVE-2022-22965.yaml`;
- регистрация и получение событий выполняются через `http://oast.test`;
- DNS-запросы для генерируемых имён обрабатывает локальный Interactsh;
- результат сохраняется в `reports/spring4shell-oast.jsonl` на компьютере.

Дождитесь завершения сканирования, включая ожидание обратных взаимодействий. Проверьте наличие находки `CVE-2022-22965` и изучите сведения об HTTP-взаимодействии, в том числе заголовок `User-Agent` Java.

Объясните последовательность проверки: регистрация Nuclei на Interactsh, отправка запроса приложению, разрешение имени и обратный HTTP-запрос со стороны Java, получение события сканером.

В стенде отключено получение публичного TLS-сертификата: для регистрации и обратного взаимодействия используется HTTP. Официальный шаблон содержит также HTTPS-проверки, для которых при такой конфигурации возможны ошибки соединения. Для срабатывания достаточно соответствующего условию шаблона HTTP-взаимодействия.

При отсутствии находки проверьте доступность приложения и журналы обоих сервисов. DNS-событие само по себе не удовлетворяет условию официального шаблона. Отсутствие результата не означает отсутствия уязвимости.

Домен `oast.test` используется только внутри стенда. Порты Interactsh не публикуются на компьютере.

8. Проанализируйте результаты и способы защиты

На основании проведённых проверок объясните:

- какие признаки опасного связывания параметров удалось обнаружить;
- почему срабатывание Nuclei и ZAP с похожим методом проверки не является независимым подтверждением RCE;
- какие дополнительные свидетельства даёт обратное HTTP-взаимодействие Java;
- почему обратное взаимодействие само по себе не доказывает выполнение произвольных команд;
- какие дополнительные сведения о конфигурации приложения необходимы для оценки возможности эксплуатации;
- как обновление Spring Framework и ограничение связывания параметров помогают устранить причину уязвимости.

9. Проверьте действие обновления Spring Framework

Соберите и запустите второй вариант приложения:

```text
docker compose build spring-fixed
docker compose up -d spring-fixed
```

Дождитесь доступности http://localhost:4001/?name=Bob&age=25. Повторите ручные запросы:

```text
curl -i 'http://localhost:4001/?name=Bob&age=25&aaa=bbb'
curl -i 'http://localhost:4001/?name=Bob&age=25&class.module.classLoader.DefaultAssertionStatus=nonsense'
```

Ожидаются HTTP 200 для обоих запросов: обычный обработчик работает, а доступ к опасному свойству блокируется на этапе связывания.

Повторите локальную проверку Nuclei, сохранив результат отдельно:

```text
docker compose run --rm nuclei -u http://spring-fixed:8080/ -t /templates/spring4shell-local.yaml -disable-update-check -no-interactsh -jsonl -o /reports/spring4shell-fixed.jsonl -no-color -stats
```

Находка `spring4shell-local-binding-check` не ожидается. Проверьте, что сканирование завершилось без ошибок и отправило запросы: пустой отчёт при недоступном приложении не подтверждает действие исправления.

Через ZAP proxy откройте http://spring-fixed:8080/?name=Bob&age=25, добавьте этот адрес в контекст и Scope и повторите Active Scan с политикой `Spring4Shell only`. Используйте результаты нового сканирования и его запросы: прежнее предупреждение для `target` может остаться в сессии.

Составьте таблицу для двух версий: ответы на контрольный и проверочный запросы, результаты Nuclei и правила ZAP 40045. Объясните, почему исчезновение находки при сохранении работоспособности страницы согласуется с исправлением механизма связывания, но не доказывает отсутствие любых других уязвимостей.

10.  Подтвердите выполнение команд на учебном стенде (необязательно)

Используя описание в [Vulhub](https://github.com/vulhub/vulhub/blob/master/spring/CVE-2022-22965/README.md), воспроизведите Spring4Shell на предоставленном приложении и проверьте возможность выполнения команд.

Перед выполнением задания сохраните результаты сканирования и пересоздайте приложение, чтобы начать проверку с исходной конфигурацией:

```text
docker compose up -d --force-recreate spring
```

Дождитесь появления страницы приложения. Изучите HTTP-запрос из раздела Vulnerability Reproduce и объясните, как изменение настроек журналирования Tomcat приводит к созданию JSP-файла.

Адаптируйте адреса из исходного описания к текущему стенду:

- при обращении с компьютера используйте `http://localhost:4000`;
- при отправке запроса через прокси ZAP используйте `http://target:8080`;
- в заголовке `Host` укажите адрес и порт выбранного способа обращения.

Отправьте подготовленный запрос через редактор запросов ZAP, сохранив параметры и специальные заголовки из исходного описания. Затем обратитесь к созданному JSP-файлу с командой `id`. При обращении с компьютера используйте адрес:

```text
http://localhost:4000/tomcatwar.jsp?pwd=j&cmd=id
```

Сохраните запрос и ответ с выводом команды. Объясните, какие данные подтверждают выполнение команды в контейнере приложения и чем это свидетельство отличается от результатов сканирования и обратного HTTP-взаимодействия.

После проверки выполните запрос очистки свойства `pattern`, приведённый в [Vulhub](https://github.com/vulhub/vulhub/blob/master/spring/CVE-2022-22965/README.md). Эта операция прекращает запись содержимого в JSP-файл, но не удаляет его. Для удаления созданного файла и восстановления исходной конфигурации пересоздайте приложение:

```text
docker compose up -d --force-recreate spring
```

Дождитесь запуска приложения и убедитесь, что обычная страница работает, а обращение к `tomcatwar.jsp` возвращает HTTP 404.
