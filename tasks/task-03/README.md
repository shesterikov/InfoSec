# Практическая работа 3

## Авторизация и разграничение доступа пользователей

### Цель работы
Получить практические навыки реализации авторизации пользователей, разграничения доступа к ресурсам на основе ролей и аудита обращений к защищенным ресурсам.

### Технические требования:
- Наличие интернет-соединения
- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/)
- Наличие [cURL](https://curl.se/download.html) / [Postman](https://www.postman.com/downloads/) / [Insomnia](https://insomnia.rest/download)
- Наличие настроенного окружения для работы с выбранным языком программирования (интерпретатор, компилятор, менеджер зависимостей [при необходимости])

### Технические ограничения:
Допускается использование следующих языков программирования и HTTP-фреймворков:
- TypeScript / [NestJS](https://nestjs.com/)
- Java / [Spring Framework](https://spring.io/) / [Spring Boot](https://spring.io/projects/spring-boot)
- Python / [Django](https://www.djangoproject.com/) / [Flask](https://flask.palletsprojects.com/) / [FastAPI](https://fastapi.tiangolo.com/)
- Go / [Gin](https://gin-gonic.com/) / [Fiber](https://gofiber.io/) / [Echo](https://echo.labstack.com/) / [Beego](https://beego.vip/)
- PHP / [Laravel](https://laravel.com/)

### Постановка задачи:
В рамках работы необходимо реализовать механизм выдачи и проверки JWT-токенов, ограничение доступа к отдельным ресурсам в зависимости от роли пользователя, а также регистрацию событий доступа в базе данных.

Данная практическая работа является продолжением практической работы №2. В рамках работы необходимо расширить разработанное ранее приложение.

Если реализация практической работы №2 выполнена на другом языке или с использованием другого фреймворка, допускается реализовать практическую работу №3 как отдельное приложение. При этом необходимо самостоятельно реализовать необходимые для работы сущности и API.

### Ход работы:
1. Расширьте модель пользователя
Добавьте в модель пользователя информацию о его роли.

Для работы необходимо предусмотреть как минимум две роли:

- user — обычный пользователь;
- admin — пользователь с расширенными правами.

Способ хранения роли, название поля, структура таблицы и тип данных определяются самостоятельно.

Для проверки работы необходимо иметь как минимум двух пользователей:

пользователя с ролью user;
пользователя с ролью admin.

Роль пользователей может быть назначена непосредственно в базе данных.

2. Добавьте поддержку JWT токенов
После успешной аутентификации пользователя необходимо сформировать JWT-токен.

В токене необходимо передавать как минимум:
- идентификатор пользователя;
- роль пользователя.

Структура остальных данных токена определяется самостоятельно.

После получения токена необходимо проверить его содержимое с использованием любого инструмента для работы с JWT, например [JWT Debugger](https://www.jwt.io/).

Убедитесь, что токен содержит идентификатор и роль пользователя.

> Не следует помещать в JWT пароль пользователя, его хеш, соль или другие конфиденциальные данные.

3. Реализуйте аутентификацию запросов
Реализуйте проверку JWT-токена для запросов к защищенным ресурсам.

Для передачи токена в запросе используйте HTTP-заголовок `Authorization: Bearer <JWT>`

При обработке защищенного запроса приложение должно:
- получить JWT-токен;
- проверить его корректность;
- определить пользователя;
- определить его роль;
- принять решение о возможности выполнения запроса.

4. Реализуйте разграничения доступа
Реализуйте как минимум следующие HTTP-ресурсы:
- `GET /all`
- `GET /users`
- `GET /admins`

Ресурс /all должен быть доступен всем пользователям, в том числе без выполнения аутентификации.
Ресурс /users должен быть доступен только аутентифицированным пользователям.
Ресурс /admins должен быть доступен только аутентифицированным пользователям с ролью admin.

Таким образом, должна быть реализована следующая модель доступа:

| Ресурс    | Неаутентифицированный пользователь |          `user` |         `admin` |
| --------- | ---------------------------------: | --------------: | --------------: |
| `/all`    |                    Доступ разрешен | Доступ разрешен | Доступ разрешен |
| `/users`  |                    Доступ запрещен | Доступ разрешен | Доступ разрешен |
| `/admins` |                    Доступ запрещен | Доступ запрещен | Доступ разрешен |

Для проверки необходимо выполнить запросы к каждому ресурсу от имени:

- неаутентифицированного пользователя;
- пользователя с ролью user;
- пользователя с ролью admin.

При отказе в доступе приложение должно возвращать соответствующий HTTP-статус.

5. Реализуйте аудит доступа
Добавьте в приложение механизм аудита обращений к защищенным ресурсам.

Информация о событиях аудита должна храниться в PostgreSQL.

Для этого необходимо самостоятельно спроектировать таблицу для хранения событий аудита.

Она должна позволять определить как минимум:
- пользователя, выполнившего запрос;
- HTTP-метод;
- запрошенный ресурс;
- дату и время выполнения запроса;
- результат проверки прав доступа.

Дополнительные поля определяются самостоятельно.

Например, структура события может содержать:
```
user_id
method
endpoint
timestamp
success
```

При этом необходимо учитывать как успешные, так и неуспешные попытки доступа.

Например, если пользователь с ролью user пытается обратиться к `GET /admins`, то такое событие должно быть зафиксировано в журнале аудита как неуспешная попытка доступа.

Аналогично необходимо фиксировать успешный доступ пользователя с соответствующими правами.

Для запросов, при обработке которых невозможно определить пользователя, например при отсутствии или некорректности JWT, допускается сохранять идентификатор пользователя как NULL.

6. Добавьте поддержку передачи JWT посредством `HTTP-only` Cookie
Добавьте возможность передачи JWT посредством HttpOnly Cookie.

Реализуйте:
- передачу JWT клиенту посредством Cookie;
- получение JWT из Cookie при обращении к защищенным ресурсам;
- проверку JWT и разграничение доступа аналогично варианту с заголовком `Authorization`.

Cookie должна иметь атрибут HttpOnly.
Проверьте, что значение Cookie с атрибутом HttpOnly недоступно клиентскому JavaScript-коду.
