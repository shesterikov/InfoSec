# Практическая работа 5

## XSS-уязвимости и способы защиты от них

### Цель работы

Получить практические навыки обнаружения, эксплуатации и устранения XSS-уязвимостей в веб-приложениях с использованием средств автоматизированного анализа и ручного тестирования.

### Технические требования

- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/)
- Наличие браузера с поддержкой современных JavaScript API.

### Постановка задачи

В ходе работы необходимо исследовать веб-приложение на наличие XSS-уязвимостей, используя инструменты автоматизированного анализа и ручного тестирования.

В качестве объекта исследования используется приложение, разработанное в рамках практической работы №4.

Необходимо пройти полный цикл работы с уязвимостью:

- провести разведку целевого приложения;
- выполнить автоматизированный поиск потенциальных уязвимостей;
- определить потенциальные места возникновения XSS;
- подтвердить наличие уязвимости вручную;
- продемонстрировать возможность её эксплуатации;
- исследовать исходный код приложения и определить причину возникновения уязвимости;
- реализовать защиту от XSS;
- настроить Content Security Policy (CSP);
- повторно проверить приложение и убедиться в устранении уязвимости.

Все действия по исследованию и эксплуатации выполняются исключительно в предоставленной практической инфраструктуре.

### Теоретические сведения

XSS (Cross-Site Scripting) — класс уязвимостей веб-приложений, при котором злоумышленник может добиться выполнения произвольного JavaScript-кода в контексте веб-страницы.

Основной причиной XSS обычно является ситуация, при которой приложение обрабатывает пользовательские данные как HTML или JavaScript-код, не выполняя необходимую проверку, экранирование или санитизацию.

В зависимости от механизма распространения можно выделить несколько основных вариантов XSS:

- Stored XSS — вредоносные данные сохраняются приложением и впоследствии передаются другим пользователям;
- Reflected XSS — вредоносные данные передаются в запросе и отражаются в ответе приложения;
- DOM-based XSS — уязвимость возникает непосредственно в клиентском JavaScript-коде при небезопасной обработке данных и изменении DOM.

Для обнаружения XSS могут использоваться как автоматизированные средства анализа, так и ручное тестирование.

В рамках работы используется OWASP ZAP для автоматизированного анализа веб-приложения.

Автоматизированный сканер не является доказательством наличия или отсутствия уязвимости. Результаты его работы необходимо проанализировать и подтвердить вручную.

Для защиты от XSS могут применяться:

- корректное экранирование пользовательских данных;
- безопасные методы работы с DOM;
- санитизация HTML;
- отказ от использования небезопасных операций вставки HTML;
- использование специализированных библиотек, например DOMPurify;
- Content Security Policy.

CSP является дополнительным механизмом защиты и не заменяет корректную обработку пользовательских данных.

### Ход работы

1. Запустите приложение

Запустите приложение при помощи команды:

```text
docker compose up -d --build
```

2. Проверьте функционирование исходного приложения

Откройте две вкладки браузера с адресом приложения: http://localhost:3000/

Отправьте сообщение из одной вкладки.

Убедитесь, что сообщение было получено второй вкладкой.


3. Подключитесь к контейнеру Kali Linux

Подключитесь к контейнеру Kali Linux:

```text
docker exec -it kali bash
```

4. Проведите автоматизированный анализ веб-приложения

Используя OWASP ZAP, проведите анализ исследуемого веб-приложения.

При проведении анализа обратите особое внимание на функциональность обмена сообщениями, реализованную в предыдущей практической работе.

Результаты работы ZAP необходимо сохранить в отчёте.

##### Примеры запуска OWASP ZAP

1. Перед запуском тестирования, убедитесь, что ZAP установлен в контейнере: 
```text
zaproxy -version
```
Если видите ошибку - Установите пакет zaproxy и пересоберите образ.

2. Для быстрого автоматического анализа приложения:

```text
zaproxy -cmd -quickurl http://target:3000
```

3. Для сохранения результата быстрого анализа в HTML-файл:

```text
zaproxy -cmd -quickurl http://target:3000 -quickout /tmp/zap-report.html
```

4. Проанализируйте результаты сканирования

Изучите обнаруженные автоматизированным сканером потенциальные уязвимости.

Для каждой интересующей точки необходимо определить:

- какой HTTP-ресурс участвует в обработке данных;
- каким образом пользовательские данные попадают в приложение;
- где эти данные отображаются;
- каким образом данные передаются между клиентом и сервером;
- почему сканер считает данную точку потенциально уязвимой.

Особое внимание необходимо уделить сообщениям, передаваемым между клиентами приложения.

Необходимо определить, может ли содержимое пользовательского сообщения интерпретироваться браузером как HTML-код.

> Важно: отсутствие XSS в отчёте ZAP не означает, что XSS отсутствует в приложении.

В отчёте необходимо зафиксировать:

- какие уязвимости обнаружил ZAP;
- обнаружил ли ZAP XSS;
- какие предупреждения были получены;
- какие части приложения были исследованы;
- какие части приложения могли остаться за пределами автоматического анализа.

###### Подтвердите наличие XSS-уязвимости с помощью Metasploit



3. Запишите IP-адрес интерфейса, доступный из сети Docker, например 172.x.x.x.

4. Запустите Metasploit:
```text

```

5. Выберите, настройте и запустите подходящий auxiliary-модуль Metasploit, который может принимать входящие HTTP-запросы. Для изучения доступных модулей используйте:
```text
search capture http
search server http
```

7. Подготовьте безопасный тестовый payload
Для подготовки payload вам понадобится следующее:

7.1 Проверьте путь данных: поле ввода → клиент → сервер → Socket.IO → другой клиент → отображение в DOM

Определите:
- отправляется ли сообщение через HTTP-запрос или WebSocket;
- сохраняется ли оно на сервере;
- получает ли его другой пользователь;
- вставляется ли оно в список сообщений, уведомление, атрибут или JavaScript-строку.

7.2. Как сообщение вставляется в DOM.
7.3. Какой это HTML-контекст.

7.4. Алгоритм сборки payload
- Проверьте доставку обычного текста
- Проверьте, интерпретируется ли HTML
- Определите разрешённые теги - Если HTML работает, проверьте нейтральные теги
- Проверьте обработчики событий - Если обычные теги проходят, проверьте, удаляются ли атрибуты on...
- Проверьте URL-контекст - Если ссылки разрешены, проверьте схему javascript:
```text
<a href="javascript:alert(1)">click</a>
```
Кликните по ссылке и наблюдайте:
появилось окно alert(1) — вектор работает;
открылась обычная страница — javascript: не выполнился;
в Console есть Refused to run the JavaScript URL — CSP блокирует выполнение

- Соберите подтверждаемый payload.

###### Устранение уязвимости
1. Устраните XSS-уязвимость

Модифицируйте исходный код приложения таким образом, чтобы пользовательские данные не могли использоваться для выполнения произвольного JavaScript-кода.

Выберите подходящий механизм защиты.

В зависимости от назначения приложения могут использоваться:

- экранирование пользовательского ввода;
- безопасные методы работы с DOM;
- санитизация HTML;
- DOMPurify;
- отказ от использования небезопасных методов вставки HTML.

После внесения изменений повторно проверьте ранее обнаруженную XSS-уязвимость.

2. Настройте Content Security Policy

Добавьте в приложение Content Security Policy.

Самостоятельно определите необходимые директивы CSP с учётом функциональности приложения.

При настройке политики обратите внимание на:

- `default-src`;
- `script-src`;
- `style-src`;
- `img-src`;
- `connect-src`.

Политика должна разрешать только те источники ресурсов, которые действительно необходимы приложению.

Проверьте работу приложения после включения CSP.

Объясните назначение выбранных директив.

3. Повторно проведите автоматизированное сканирование

После устранения XSS-уязвимости повторно проведите анализ приложения при помощи OWASP ZAP.

Сравните результаты первоначального и повторного сканирования.

Проверьте ранее обнаруженную точку вручную.

В отчёте приведите результаты повторного сканирования и укажите, какие обнаруженные ранее проблемы были устранены.

4. Повторно проведите тестирование Metasploit, чтобы убедиться, что уязвимость устранена.  

5. Проверьте работоспособность приложения после исправления

Отправьте несколько обычных сообщений между клиентами.

Убедитесь, что:

- сообщения корректно передаются;
- сообщения корректно отображаются;
- пользовательский ввод больше не приводит к выполнению JavaScript;
- добавленная CSP не нарушает штатную работу приложения;
- ранее обнаруженная XSS-уязвимость устранена.
