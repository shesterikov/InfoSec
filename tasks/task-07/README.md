# Практическая работа 7

## SQL-инъекции и способы защиты от них

### Цель работы

Получить практические навыки обнаружения, эксплуатации и устранения SQL-инъекций с использованием OWASP ZAP и ручного тестирования.

### Технические требования

- Наличие интернет-соединения
- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/)

### Постановка задачи
Исследуйте форму входа учебного чата на Go и PostgreSQL: найдите SQL-инъекцию, подтвердите обход аутентификации, исправьте код и повторите проверки. Для анализа используйте ZAP Proxy из Docker-образа.

Все действия выполняются только в предоставленной практической инфраструктуре.

### Теоретические сведения

SQL-инъекция возникает, когда пользовательские данные изменяют структуру SQL-запроса. Для защиты используются параметризованные запросы: SQL-код и значения передаются отдельно. В PostgreSQL с драйвером `lib/pq` применяются параметры `$1`, `$2` и далее.

Пароли в приложении хранятся как bcrypt-хеши и проверяются функцией `crypt`. Хеширование паролей не защищает от SQLi. Результаты сканера необходимо подтверждать вручную; отсутствие предупреждений не доказывает отсутствие уязвимости.

### Ход работы

1. Запустите стенд

Из каталога `tasks/task-07` выполните:

```text
docker compose up -d --build --wait
```

Откройте http://localhost:8080. При ошибках проверьте `docker compose ps` и `docker compose logs app db zap`.

2. Проверьте работу приложения

| Имя пользователя | Пароль |
| --- | --- |
| `student` | `student123` |
| `admin` | `admin123` |

Войдите, отправьте сообщение и проверьте общую историю из другого браузера. Убедитесь, что неверный пароль отклоняется, а после выхода чат недоступен.

3. Настройте ZAP Proxy

Откройте http://127.0.0.1:8081/zap в браузере без прокси и дождитесь рабочего окна ZAP.

В отдельном профиле браузера настройте HTTP-прокси `127.0.0.1:8091` и откройте http://target:8080. Используется HTTP; SOCKS и сертификат ZAP не требуются.

Если соединение не работает, проверьте открытие интерфейса ZAP и настройки прокси:

```text
curl --noproxy "" --proxy http://127.0.0.1:8091 http://target:8080/health
```

Ожидается HTTP 200.

4. Изучите запрос формы входа

Выполните правильный и неправильный вход через прокси. Найдите `POST /login` в History ZAP, определите поля формы, статусы ответов, перенаправление и cookie `sqli_session`.

Успешный вход возвращает HTTP 303 и новую cookie, неверные данные — HTTP 401. Сохраните запросы и ответы.

5. Проведите автоматизированное сканирование

Добавьте `http://target:8080` в Context/Scope и выберите режим Protected. Запустите Active Scan успешного `POST /login` с данными `student / student123`.

Параметры сканирования:

- POST Data включён;
- правило SQL Injection, Strength Medium, Threshold Medium;
- PostgreSQL не исключена в Technologies.

Проверьте, что сканер изменяет оба поля формы. При отсутствии находок изучите отправленные запросы и при необходимости повторите со Strength High и Threshold Low. Сохраните настройки, версию ZAP, результаты и примеры запросов в `reports/before` на компьютере.

6. Подтвердите SQL-инъекцию и выполните обход аутентификации

Повторите запросы в редакторе ZAP.

Используя SQL-инъекцию, выполните обход аутентификации (authentication bypass): получите доступ к чату с непустым неверным паролем. Предварительно выйдите из системы и удалите старую cookie из запроса. Подтвердите доступ с новой сессией и укажите, под каким пользователем выполнен вход.

7. Найдите причину и исправьте код

Изучите `internal/web/auth.go` и `internal/store/users.go`. Объясните, как ввод меняет SQL, и замените построение строки параметризованным запросом для обоих полей. Сохраните проверку пароля через `crypt`.

Пересоберите приложение:

```text
docker compose up -d --build --wait app
```

8. Повторите проверки

Запустите новый Active Scan с прежними настройками и сохраните результаты в `reports/after`. Отличайте новые результаты от старых предупреждений ZAP.

Вручную проверьте правильный и неправильный вход, прежний обход и апостроф в каждом поле. Обычный вход должен работать, а тестовый ввод — отклоняться без SQL-ошибки. Проверьте выход и отправку сообщений. Перед проверкой обхода завершите старую сессию: пересборка её не удаляет.

9. Подготовьте отчёт и остановите стенд

Включите в отчёт результаты ZAP до и после исправления, запросы ручной проверки, объяснение обхода и изменения кода. Не включайте действующие cookie и полные хеши паролей.

Сохраните файлы на компьютере; отчёты из контейнера ZAP скачайте средствами Webswing. Затем выполните:

```text
docker compose down
```

Данные сохраняются. Для полного сброса сообщений, сессий и данных ZAP используйте `docker compose down -v`. После работы отключите прокси в браузере.
