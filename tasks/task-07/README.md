# Практическая работа 7

## SQL-инъекции и способы защиты от них

### Цель работы

Получить практические навыки обнаружения, эксплуатации и устранения SQL-инъекций в веб-приложениях с использованием средств автоматизированного анализа и ручного тестирования.

### Технические требования

- Наличие [Docker](https://docs.docker.com/desktop/) и [Docker Compose](https://docs.docker.com/compose/install/)
- Наличие браузера с возможностью настройки HTTP-прокси.
- Наличие интернет-соединения для загрузки Docker-образов и зависимостей.

### Постановка задачи

В ходе работы необходимо исследовать веб-приложение на наличие SQL-инъекций, используя инструменты автоматизированного анализа и ручного тестирования.

В качестве объекта исследования используется учебный чат на Go и PostgreSQL. Для автоматизированного анализа используется OWASP ZAP, запускаемый в Docker с веб-интерфейсом Webswing.

Необходимо пройти полный цикл работы с уязвимостью:

- исследовать форму входа и HTTP-запросы приложения;
- выполнить автоматизированный поиск потенциальных SQL-инъекций;
- подтвердить наличие уязвимости вручную;
- продемонстрировать обход аутентификации;
- исследовать исходный код и определить причину возникновения уязвимости;
- реализовать защиту с использованием параметризованных запросов;
- повторно провести атаку и автоматизированное сканирование;
- проверить работоспособность приложения после исправления.

Все действия по исследованию и эксплуатации выполняются исключительно в предоставленной практической инфраструктуре.

### Теоретические сведения

SQL-инъекция (SQLi) — класс уязвимостей, при котором пользовательские данные могут изменять структуру SQL-запроса.

Основной причиной SQL-инъекций является включение пользовательского ввода в текст запроса без отделения данных от SQL-кода.

Для защиты используются параметризованные запросы: SQL-код и значения передаются отдельно. В PostgreSQL с драйвером `lib/pq` применяются параметры `$1`, `$2` и далее.

Пароли в приложении хранятся как bcrypt-хеши и проверяются функцией `crypt`. Хеширование паролей не защищает от SQL-инъекций и не заменяет безопасное построение запросов.

Автоматизированный сканер не является доказательством наличия или отсутствия уязвимости. Результаты его работы необходимо проанализировать и подтвердить вручную.

### Ход работы

1. Запустите стенд

Запустите стенд при помощи команды:

```text
docker compose up -d --build --wait
```

Откройте http://localhost:8080.

При ошибках проверьте состояние контейнеров командой `docker compose ps` и журналы командой `docker compose logs app db zap`.

2. Проверьте функционирование исходного приложения

Используйте следующие учётные данные:

| Имя пользователя | Пароль |
| --- | --- |
| `student` | `student123` |
| `admin` | `admin123456` |

Войдите в приложение и отправьте сообщение.

Откройте приложение в другом браузере, выполните вход и убедитесь, что сообщение отображается в общей истории. Для получения новых сообщений обновите страницу.

Проверьте, что вход с неверным паролем отклоняется, а после выхода из системы чат недоступен без повторного входа.

3. Настройте ZAP Proxy

Откройте http://127.0.0.1:8081/zap в браузере без прокси и дождитесь рабочего окна ZAP.

В отдельном профиле браузера настройте HTTP-прокси `127.0.0.1:8091` и откройте http://target:8080.

Адрес `target` доступен внутри Docker-сети; обращайтесь к нему через настроенный прокси. Используется HTTP, поэтому настройка SOCKS и установка сертификата ZAP не требуются.

Если соединение не работает, проверьте открытие интерфейса ZAP и настройки прокси:

```text
curl --noproxy "" --proxy http://127.0.0.1:8091 http://target:8080/health
```

Ожидается HTTP 200.

4. Изучите запрос формы входа

Выполните вход с правильными и неправильными учётными данными через прокси.

Найдите `POST /login` на вкладке History в ZAP.

Определите:

- какие поля формы передаются в запросе;
- какие HTTP-статусы возвращает приложение;
- куда выполняется перенаправление после успешного входа;
- как устанавливается cookie сессии `sqli_session`.

Успешный вход возвращает HTTP 303 и новую cookie. Неверные учётные данные при допустимом формате полей возвращают HTTP 401. Пустые поля, превышение допустимой длины (100 символов для имени, 200 для пароля) и ошибки выполнения SQL возвращают HTTP 400; различайте их по сообщению в ответе.

Сохраните запросы и ответы для отчёта.

5. Проведите автоматизированное сканирование

Добавьте `http://target:8080` в контекст ZAP и включите его в область сканирования (Scope). Выберите режим Protected.

Запустите Active Scan для ранее перехваченного успешного запроса `POST /login` с данными `student / student123`.

Параметры сканирования:

- POST Data включён;
- правило SQL Injection, Strength Medium, Threshold Medium;
- PostgreSQL не исключена в Technologies.

Проверьте, что сканер изменяет оба поля формы.

При отсутствии находок изучите отправленные запросы и при необходимости повторите сканирование со Strength High и Threshold Low.

Сохраните настройки, версию ZAP, результаты и примеры запросов в `reports/before` на компьютере. Если настройки менялись, зафиксируйте параметры каждого запуска для последующего сравнения.

6. Подтвердите SQL-инъекцию и выполните обход аутентификации

На основании проведённого анализа самостоятельно разработайте тестовый ввод для проверки SQL-инъекции. Повторите запросы в редакторе ZAP и объясните, какие ответы подтверждают наличие уязвимости.

Используя SQL-инъекцию, выполните обход аутентификации (authentication bypass): получите доступ к чату с непустым неверным паролем. Предварительно выйдите из системы и удалите старую cookie из запроса. Подтвердите доступ с новой сессией и укажите, под каким пользователем выполнен вход.

7. Найдите причину уязвимости и исправьте код

Изучите `internal/web/auth.go` и `internal/store/users.go`.

Определите:

- как данные формы попадают в SQL-запрос;
- какая операция позволяет пользовательскому вводу менять структуру запроса;
- почему проверка хеша пароля не предотвращает обход аутентификации.

Объясните причину возникновения уязвимости.

Замените построение строки SQL параметризованным запросом для обоих полей формы. Сохраните проверку пароля через `crypt`.

Пересоберите приложение:

```text
docker compose up -d --build --wait app
```

8. Проверьте результат исправления

Повторите ранее успешную атаку. Перед проверкой завершите старую сессию и удалите её cookie из запроса: пересборка приложения не удаляет сохранённые сессии. Убедитесь, что теперь атака не позволяет получить доступ к чату.

Повторите Active Scan с прежними настройками. Проверьте, обнаруживает ли ZAP SQL-инъекцию после исправления.

Сопоставьте результаты ручной атаки и ZAP и сделайте вывод об эффективности исправления. Отсутствие предупреждений сканера само по себе не доказывает устранение уязвимости.

Дополнительно убедитесь, что обычный вход, отправка сообщений и выход из системы работают.

9. Подготовьте отчёт и остановите стенд

В отчёте приведите:

- настройки и результаты ZAP до и после исправления;
- запросы и ответы ручной проверки;
- подтверждение обхода аутентификации и имя пользователя, под которым выполнен вход;
- объяснение причины уязвимости и внесённых изменений;
- результаты повторной атаки и проверки работоспособности приложения;
- вывод об эффективности исправления.

Не включайте действующие cookie и полные хеши паролей.

Сохраните файлы на компьютере. Отчёты из контейнера ZAP скачайте средствами Webswing.
